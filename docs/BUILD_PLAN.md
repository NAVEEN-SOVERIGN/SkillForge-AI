# Build plan

## Architecture decision to validate in the first milestone

Ship one React and TypeScript application with one same-origin FastAPI API, scalable analysis workers and a separate assessment evaluator. FastAPI is proposed because Hackfront already defines the indexing and account behavior there. Bring over SkillForge career calculations through versioned contracts once GitHub import, scoring, code graphs and scenario-based tests work together.

- PostgreSQL is authoritative for identities, sessions, career data, approvals, evidence, consent and job status. Use versioned migrations and a durable job table with leases, bounded retries and idempotency keys. Review managed PostgreSQL capacity under measured workload.
- Neo4j holds the repository graph projection, scoped by owner and snapshot. Review existing Aura schema and capacity with staging credentials before rollout. Workers publish replacement snapshots and retire old ones only after the new snapshot is available. PostgreSQL remains authoritative for access. Delete or expire access first and durably reconcile graph cleanup.
- Define typed contracts for repository snapshots, citations, proof, readiness reports and jobs. Pin source links to revision where supported. Re-indexing preserves historical citation references and records their availability. Deduplicate proofs and score changes in a transaction. Durable portfolio evidence from a temporary workspace needs a separate explicit retention action and can retain a citation reference without retaining the index.
- Keep GitHub reads bounded with a shared quota state across replicas. Preserve the 10 uncached REST requests per default Hackfront import as the initial baseline. Fetch expanded evidence such as ADRs and focused discussions through a separately metered job. Keep rate-limit headers, cancellation, capped concurrency, coalescing and cache behavior visible in telemetry.
- AI adapters expose a deterministic path, optional server-managed Gemini and tab-scoped BYOK for user-selected compatible providers. Validate response schemas and citation IDs. Make routing explicit, obtain consent before transmitting evidence, and keep provider credentials and content out of logs. Publish a privacy-safe evidence-only fallback for assistant and a deterministic advisory fallback for coaching.
- Pin scans to repository, commit, rubric, analyzers and model configuration. Parse bounded source and project metadata into file, package, symbol and call-site records. Derive import and call edges from language-aware resolvers. Persist provenance and resolution state alongside the graph. Expose graph search and expansion from the same projection. Calculate comparative scores only within supported cohorts, with independently measured coverage and documented quality gates.
- Separate learner submissions from repository data and control-plane services. The evaluator receives only the versioned problem, permitted runtime, submission and bounded test inputs. Run each job in a disposable no-network environment with time, memory, process and output limits. Pass back structured results with no credentials or hidden inputs. Verify runtime isolation before exposing submissions publicly.

## Release gates

- **Correctness and security.** Pass locked dependency installs, frontend type checks and production build, API lint and tests, dependency and secret scans, migration tests and browser checks. Verify identity isolation, GitHub connection revocation, graph edge resolution, rubric reproducibility, citation abstention, and inert rendering of user and repository text. Check that import networks are limited to approved GitHub hosts, including on redirect. Confirm judge isolation and inspect output for hidden tests or credentials. Review retention and privacy disclosures before public onboarding.
- **Resilience.** Test worker pause and restart, duplicate delivery, concurrent writes, upstream throttling, completion retry, and graph, email and AI outages. Confirm deletion and expiry propagate after worker restart. Schedule a restore and rollback drill with data consistency checks.
- **Initial reliability targets.** Propose 99.9% monthly availability for authenticated core career routes, p95 under 500 ms on core reads at 50 concurrent staging users, 2-hour temporary workspace inactivity TTL, cleanup within 24 hours, RPO of 24 hours and RTO of 4 hours. Measure against staging with representative workloads and separate upstream service timing before approving targets. Imports report progress soon after acceptance and use provider reset timestamps when queued for quota.
- **Usability.** Verify keyboard operation and alternatives to graph-only interactions, mobile use, loading/empty/partial/error states, PDF rendering, and coverage/consent copy in the end-to-end release flow.
- **Operations.** Require production secrets in the deployer's secret store, monitored health and queue lag, redacted logs with request and job IDs, alert ownership, restore evidence, an audited rollout and rollback procedure, and an environment-by-environment sign-off. Deploy first to staging and then a limited pilot.

## Data migration and decisions

- Assume a fresh production database until an owner confirms which real users or indexes must migrate. Use synthetic staging fixtures. For an approved migration, inventory account IDs and evidence ownership, dry-run on an isolated copy, reconcile counts and references per user, define rollback and require reauthentication. Never merge identities based solely on matching email.
- Confirm branding, upstream reuse permission, hosting and spend, provider enablement, production retention and privacy wording, and any real data migration with the owner before the relevant release work. Keep architecture defaults and pilot targets open until measured.
